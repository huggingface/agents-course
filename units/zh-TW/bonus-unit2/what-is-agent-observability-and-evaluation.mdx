# AI agent 的可觀測性與評估

## 🔎 什麼是可觀測性？

可觀測性是指透過日誌、指標與追蹤紀錄等外部訊號，了解 AI agent 的內部狀況。對 AI agent 而言，這包括追蹤行動、工具使用、模型呼叫與回應，以便除錯並改善表現。

![可觀測性儀表板](https://huggingface.co/datasets/agents-course/course-images/resolve/main/en/bonus-unit2/langfuse-dashboard.png)

## 🔭 為什麼 agent 的可觀測性很重要？

缺乏可觀測性時，AI agent 就像「黑箱」。可觀測性工具能揭示 agent 的運作，讓你：

- 了解成本與準確度之間的取捨
- 測量延遲
- 偵測有害語言與 prompt injection
- 監控使用者回饋

換句話說，可觀測性能幫助你的展示用 agent 準備好進入正式環境！

## 🔨 可觀測性工具

常見的 AI agent 可觀測性工具包括 [Langfuse](https://langfuse.com) 與 [Arize](https://www.arize.com) 等平台。這些工具能收集詳細的追蹤紀錄，並提供儀表板來即時監控指標，讓你更容易發現問題、改善效能。

不同可觀測性工具的功能與能力差異很大。有些工具採用開源模式，龐大社群會參與規劃發展方向，並提供豐富的整合功能。有些工具專注於 LLMOps 的特定面向，例如可觀測性、評估或 prompt 管理；另一些則涵蓋完整的 LLMOps 工作流程。我們鼓勵你閱讀各種工具的文件，選出適合自己的方案。

許多 agent 框架，例如 [smolagents](https://huggingface.co/docs/smolagents/v1.12.0/en/index)，會使用 [OpenTelemetry](https://opentelemetry.io/docs/) 標準，將中繼資料提供給可觀測性工具。此外，可觀測性工具也會開發自訂監測整合，以更靈活地因應快速演進的 LLM 技術。請查閱所用工具的文件，確認支援哪些功能。

## 🔬 Trace 與 span

可觀測性工具通常會以 trace 和 span 表示 agent 的執行過程。

- **Trace（追蹤紀錄）** 代表 agent 從頭到尾的一次完整任務，例如處理使用者查詢。
- **Span（追蹤區段）** 是 trace 中的個別步驟，例如呼叫語言模型或擷取資料。

![Langfuse 中的 smolagent trace 範例](https://huggingface.co/datasets/agents-course/course-images/resolve/main/en/bonus-unit2/trace-tree.png)

## 📊 值得監控的關鍵指標

以下是可觀測性工具最常監控的一些指標：

**延遲：** agent 回應有多快？等待過久會影響使用者體驗。你應透過追蹤 agent 的執行過程，測量整體任務與各步驟的延遲。例如，如果一次任務中所有模型呼叫共花費 20 秒，可以考慮使用更快的模型，或平行呼叫模型來加速。

**成本：** agent 每次執行的費用是多少？AI agent 會呼叫按 token 計費的 LLM 或外部 API。頻繁使用工具或多次送出 prompt，可能讓成本快速增加。例如，若 agent 呼叫 LLM 五次，品質卻只略有改善，就應評估這筆成本是否值得，以及能否減少呼叫次數或改用較便宜的模型。即時監控也能幫助你找出異常的成本飆升，例如程式錯誤造成 API 過度循環呼叫。

**請求錯誤：** agent 有多少請求失敗？這可能包括 API 錯誤或工具呼叫失敗。你可以設定備援方案或重試機制，讓 agent 在正式環境中更能承受這些問題。例如，LLM 供應商 A 的服務中斷時，就切換到供應商 B。

**使用者回饋：** 讓使用者直接評價能提供寶貴資訊，包括明確評分（👍／👎、⭐1 至 5 顆星）或文字意見。持續出現負面回饋時就該留意，因為這表示 agent 可能未如預期運作。

**隱性使用者回饋：** 即使使用者沒有明確評分，也能從行為取得間接回饋，例如立刻改寫問題、重複查詢或點選重試按鈕。若使用者反覆詢問同一個問題，就可能表示 agent 的表現未達預期。

**準確度：** agent 多常產生正確或符合期望的輸出？準確度的定義因情境而異，例如解題正確率、資訊檢索準確度或使用者滿意度。首先，要定義你的 agent 怎樣才算成功。接著可透過自動化檢查、評估分數或任務完成標籤追蹤準確度，例如將 trace 標記為「成功」或「失敗」。

**自動化評估指標：** 你也可以設定自動化評估，例如讓 LLM 為 agent 的輸出評分，判斷內容是否有幫助、是否正確。還有多種開源函式庫可以評估 agent 的不同面向，例如用於 RAG agent 的 [RAGAS](https://docs.ragas.io/)，以及用來偵測有害語言或 prompt injection 的 [LLM Guard](https://llm-guard.com/)。

實務上，結合多種指標才能更全面地掌握 AI agent 的狀況。本章的[範例 notebook](https://colab.research.google.com/#fileId=https://huggingface.co/agents-course/notebooks/blob/main/bonus-unit2/monitoring-and-evaluating-agents.ipynb) 會展示這些指標的實際案例。不過，我們先來看看典型的評估流程。

## 👍 評估 AI agent

可觀測性提供指標；評估則是分析這些資料、執行測試，判斷 AI agent 的表現以及可以改進的地方。換句話說，取得 trace 與指標後，要如何用它們來評斷 agent 並做出決策？

定期評估很重要，因為 AI agent 的行為往往不具確定性，也可能因更新或模型行為漂移而改變。如果不評估，就無法知道你的「聰明 agent」是否確實完成工作，或表現是否退步。

AI agent 的評估分為**線上評估**與**離線評估**。兩者都有價值，也能互補。我們通常從離線評估開始，因為這是部署任何 agent 之前至少要完成的步驟。

### 🥷 離線評估

![Langfuse 中的資料集項目](https://huggingface.co/datasets/agents-course/course-images/resolve/main/en/bonus-unit2/example-dataset.png)

離線評估是在受控環境中評估 agent，通常使用測試資料集，而非即時的使用者查詢。你會準備已知預期輸出或正確行為的資料集，再讓 agent 處理這些資料。

例如，若你開發了數學應用題 agent，可以準備一份包含 100 道已知答案題目的[測試資料集](https://huggingface.co/datasets/gsm8k)。離線評估通常在開發期間執行，也可以納入 CI/CD 流程，確認是否有所改善，並防止退步。優點是**可以重複執行，而且因為有標準答案，能取得明確的準確度指標**。你也可以模擬使用者查詢，將 agent 的回應與理想答案比較，或使用前述自動化指標。

離線評估的主要挑戰，是確保測試資料集涵蓋夠全面，而且持續符合實際需求。agent 可能在固定測試集上表現很好，卻在正式環境中遇到截然不同的查詢。因此，應持續加入新的邊界案例與反映真實情境的範例。結合少量「冒煙測試」案例與較大的評估集很有幫助：小型資料集用於快速檢查，大型資料集則提供更全面的效能指標。

### 🔄 線上評估

線上評估是在真實、即時的環境中，也就是正式環境的實際使用過程中，評估 agent。這包括持續監控 agent 與真實使用者互動時的表現，並分析結果。

例如，你可以追蹤實際流量中的成功率、使用者滿意度或其他指標。線上評估的優點是**能捕捉實驗環境中未預料到的情況**：你可以觀察模型隨時間產生的漂移，例如輸入模式改變後 agent 的效果是否變差，也能發現測試資料未涵蓋的意外查詢或情境。這能真實呈現 agent 在實際環境中的行為。

如前所述，線上評估通常會收集隱性與明確的使用者回饋，也可能進行影子測試或 A/B 測試，讓新版 agent 與舊版平行執行以便比較。挑戰是，實際互動往往不容易取得可靠的標籤或分數，因此可能需要依靠使用者回饋或後續指標，例如使用者是否點選結果。

### 🤝 結合兩種方法

實務上，成功的 AI agent 評估會結合**線上**與**離線**方法。你可以定期執行離線基準測試，量化 agent 在指定任務上的表現，同時持續監控實際使用狀況，找出基準測試遺漏的問題。例如，離線測試可以確認程式碼生成 agent 在已知題目集上的成功率是否提升；線上監控則可能提醒你，使用者開始詢問一類 agent 難以處理的新問題。結合兩者，才能更完整地掌握狀況。

許多團隊會採用這樣的循環：_離線評估 → 部署新版 agent → 監控線上指標並收集新的失敗案例 → 將案例加入離線測試集 → 持續迭代_。如此一來，評估就能持續進行、不斷改善。
