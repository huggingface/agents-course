# 什麼是 `LangGraph`？ [[what-is-langgraph]]

`LangGraph` 是 [LangChain](https://www.langchain.com/) 開發的框架，**用來管理整合 LLM 的應用程式的控制流程**。

## `LangGraph` 與 `LangChain` 有何不同？

LangChain 提供與模型及其他元件互動的標準介面，適用於檢索、LLM 呼叫與工具呼叫。
LangGraph 可以使用 LangChain 的類別，但並非必要。

這兩個套件各自獨立，可以單獨使用，不過網路上的資源通常會搭配使用兩者。

## 什麼時候該使用 `LangGraph`？
### 控制與自由度

設計 AI 應用程式時，會面臨**控制**與**自由度**之間的基本取捨：

- **自由度**給 LLM 更多發揮創意、處理意外問題的空間。
- **控制**讓你確保行為可預測，並維持防護措施。

*smolagents* 中的 Code agent 自由度很高，能在一個行動步驟中呼叫多個工具、建立自己的工具等。不過，與一般使用 JSON 的 agent 相比，這也可能讓它們更難預測和控制！

`LangGraph` 位於另一端：當你需要**控制** agent 的執行時，它特別適合。

需要**掌握應用程式的運作流程**時，LangGraph 很有價值。它提供工具，讓應用程式遵循可預測的流程，同時運用 LLM 的能力。

簡單來說，如果應用程式有一連串步驟，需要按特定方式協調，並在每個交會點做出決策，**LangGraph 就能提供所需的結構**。

舉例來說，假設我們要建立能回答文件相關問題的 LLM 助手。

由於 LLM 最擅長理解文字，回答問題前，需要先將圖表、表格等其他複雜模態轉換為文字。不過，要怎麼轉換，取決於文件的類型！

LangGraph 特別適合的情境包括：

- 需要明確控制流程的**多步驟推理**
- **需要在步驟之間持續保留狀態的應用程式**
- **結合確定性邏輯與 AI 能力的系統**
- **需要人工介入的工作流程**
- 多個元件協作的**複雜 agent 架構**

也就是說，只要**你能親自**根據各項行動的輸出設計流程，並決定接下來執行什麼，LangGraph 就很適合你！

在我看來，`LangGraph` 是目前最適合部署至正式環境的 agent 框架。

## LangGraph 如何運作？

`LangGraph` 的核心，是透過有向圖結構定義應用程式的流程：

- **節點**代表個別處理步驟，例如呼叫 LLM、使用工具或做出決策。
- **邊**定義步驟之間可能的轉換。
- **狀態**由使用者定義並維護，執行時在節點之間傳遞。決定下一個節點時，依據的就是目前狀態。

下一章會更深入探索這些基本要素！

## 和一般 Python 有何不同？為什麼需要 LangGraph？

你可能會想：「直接寫一般 Python 程式碼，用 if-else 敘述處理這些流程就好了吧？」

技術上確實可行，但建立複雜系統時，LangGraph 比原生 Python **多了一些優勢**。你可以不使用 LangGraph 建立相同應用程式，但它提供更方便的工具與抽象概念。

其中包括狀態、視覺化、記錄（追蹤紀錄）、內建人工介入功能等。
